GraphRAG retrieval over SEC filings

Structured retrieval runs end to end against a real Microsoft FY2025 10-K — and it was blocked for days by two components that were each individually correct. The failure only existed in the composition, which means no amount of reading either side would have found it.

Financial question answering over filings has a verification problem rather than a fluency problem. A language model will happily produce a revenue figure; what an auditor needs is the figure plus the filing, the period, the accession number and the exact fact it came from. This system answers questions over SEC filings through a knowledge graph and a structured fact store, and returns evidence carrying provenance rather than prose carrying a number.

I own the retrieval layer. A question enters a public retrieval interface, passes contract validation, dispatches to a registered backend, and comes back as validated evidence. Against a DuckDB store rebuilt from the real Microsoft FY2025 10-K, a revenue query returns three fiscal years — 72.9bn, 87.5bn, 106.3bn — each row carrying its period, its filing date and a content-addressed fact ID that traces to the source document.

The blocker is the part worth telling. The query layer matched the backend interface exactly, so registration was a single line with no adapter needed. But the fact table stored period start, period end and period type, and had no filing-date column at all — while filing date was not on the nullable list in the evidence contract. So every row failed validation, including every correct one. Both halves were defensible in isolation. The fix was to add the column rather than relax the contract, and to look the filing date up from EDGAR metadata rather than let anyone type it, since it is not tagged inside the document. Relaxing the contract would have weakened the envelope for every other retrieval arm to patch one.

Demoing that fix surfaced a second defect immediately: a reporting-period field was a hardcoded date literal, so a single query spanning three fiscal years produced rows whose envelope contradicted their own metadata. It was visible in the very first real output and invisible in every test. That pair of bugs is why I now treat "ran it against real data once" as a different category of evidence from "the tests pass" — and why I keep asking, of every field in a response envelope, whether it came from the data or was typed by a person.

The toy graph above exists to make retrieval failures arguable before they are expensive. It encodes the two cases that break naive approaches: an ambiguous one-hop traversal where two defensible paths reach different facts, and a restatement where the same metric is reported twice across filings with different values. A retriever that cannot say which one it chose, and why, is not usable for audit work regardless of how well it reads.

Status, stated precisely. Structured retrieval works end to end. The graph arm does not — the Cypher retriever is not written, and that is on my card. Extraction feeds the graph store on a separate path that is not yet joined to retrieval, and no entity resolution exists in the query path. The honest sentence is "structured retrieval works end to end," never "the pipeline works."

Stack: Python · DuckDB · Neo4j / Cypher · EDGAR API · pytest (112 passing)

Role: retrieval layer — contract design · backend dispatch · evidence validation · provenance envelope

Columbia University capstone, sponsored by KPMG, 2026. Team of five; extraction, evaluation and abstention are teammates' work.

What I'd do next: write the Cypher retriever so the graph arm answers at all, join extraction to the query path, and replace the two remaining hardcoded envelope fields — they are correct for exactly one company and wrong the moment a second filing lands.
